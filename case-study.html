From a stack of photos to a standings site

Data cleanup Static site, no build step Vanilla JS Design system Anonymized data, fictional names

The problem

Our club runs informal doubles round robins — 12 to 14 pairs, games to 18 points, everyone rotating through 11 rounds. The results exist as photos of paper scoresheets: some typed and printed, most handwritten with corrections, spread across a folder of nearly-identical filenames. There was no way to look at the season, compare two tournament days, or spot a trend without re-reading a stack of photos every time.

Turning photos into structured data

The first pass was transcription, not visualization. Each tournament day has two kinds of source: a numbered legend mapping a pair to a color/number, and a set of tables — either printed totals (games won, points scored, final placement) or handwritten per-round match sheets.

The handwritten round-by-round sheets turned out to be too unreliable to trust: corrected numbers, crossed-out scores, and inconsistent handwriting made several individual match scores genuinely ambiguous. Rather than guess, this project only encodes what could be verified — and it was verified: total wins recorded for each pair summed exactly to the number of matches actually played (66 for a 12-pair day, 77 for 14 pairs), which is a hard mathematical check that the transcription was accurate, even without being able to read every handwritten cell.

Why a data file per tournament, not a hardcoded page

The first version of this project was a single HTML file with the numbers typed directly into the page. That's fine for one tournament; it doesn't scale to a season. So the structure changed: every tournament day is now its own JSON file in data/tournaments/, listed in data/manifest.json. The site fetches those files, computes standings, win rates, and points rankings on the fly, and renders them — meaning a new tournament day is a new JSON file, not a new pull request against the markup.

The schema also had room to grow: a rounds field was built early to hold real match-by-match scores (court, teams, final score), ready for whenever a tournament's data was clean enough to capture at that level. That happened sooner than expected — see below.

From three tournaments to a full season

The site started with three tournament days, hand-transcribed from photos as described above. Later, a much larger export from the same club's own records became available: 19 tournaments from May through September, 1,485 individual matches, with real per-round scores for every one of them — not just day totals. That's the dataset the site runs on now.

The export anonymizes every player (P001…P108) and pair (T01-01, etc.) on purpose, with no id-to-name mapping included — a deliberate privacy choice by whoever prepared it, not an oversight. Since this site is a portfolio piece, not a tool the real club uses to look up real people, the fix was to assign a fictional Estonian name to each anonymized id and keep that mapping stable across the whole dataset: the same fictional person, in every tournament they "played." Every name shown anywhere on this site is a placeholder — the results, dates, scores, and standings math are real; the identities behind them are not.

Four of the 19 tournaments ran as two simultaneous, independent groups — e.g. twelve pairs on one set of courts and eight on another, playing to their own separate standings table at the same time. The source data was explicit that mixing those two groups into one ranked list would misrepresent results neither group actually produced. So the schema grew a group field per pair, and the standings math (groupSlices() in js/app.js) ranks each group independently — a grouped tournament renders as two separate sections on the standings page, each with its own champion, stat row, and full standings.

Design decisions

The visual language leans directly into the subject — a deep court green, chalk-white court lines, and gold/silver/bronze reserved strictly for podium finishes rather than spread across every category. Headlines use a condensed poster face (Anton) for a scoreboard feel; scores and stats sit in a monospace face (JetBrains Mono) so the digits line up like they would on an actual scoreboard.

Rather than a wall of numbers, each tournament section leads with a stat row (champion, matches played, low score of the day) before the full ranked list — the summary comes before the detail, the way you'd actually want to scan a results board.

The "Players" view

Pairs change from tournament to tournament, but people don't. The Players page splits each pair name and aggregates every individual's appearances, total wins, and win rate across every tournament they've played — computed automatically from the same tournament files, with no separate player list to keep in sync.

What's next

  • A match-log view: the rounds field now holds real per-round scores for every tournament, but nothing on the site renders it yet — it would unlock head-to-head records and per-round streaks.
  • More tournament days, same JSON schema — the standings, points boards, and returning-pairs comparisons all update automatically.
  • Individual player pages with their full result history.

Stack

Plain HTML, CSS, and JavaScript — no framework, no build step, no dependencies. Data lives in versioned JSON files rather than a database, so the whole project's history is just its git log. Deployable as static files to GitHub Pages, Vercel, or Netlify.

Built as a personal project analyzing club badminton results. See README.md in the repository for how to add new tournament data.
